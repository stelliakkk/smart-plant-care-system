# 系统架构

> 一句话概括：**ESP32 负责"感知与执行"，后端负责"记录与决策"，前端负责"展示与交互"。**

## 2. 三条数据流

### ① 上行：传感器数据（✅ 已打通）

```
BH1750 光照 / 电容式土壤探头
  → ESP32 每秒采样 → 每 3 秒发 MQTT plant/edge01/telemetry（QoS 0）
  → 后端 mqtt/client 收到 → telemetry_service 入库（SQLite）
  → 前端每 3 秒轮询 GET /api/telemetry/latest → 页面数字跟着动
```

另有一条 `plant/edge01/status` 心跳（每 3 秒，带 RSSI / uptime / fault）。
后端超过 **30 秒**收不到任何上行报文就判定设备离线。

> 盐分和温度**目前上报 `null`**（传感器未接入）。后端允许任一字段为 `null`，
> 所以不会因此丢弃整条数据 —— 这是"先接通链路、再补传感器"的前提。
>
> WebSocket 推送目前仍是待做项：3 秒轮询已经够用，而且排查起来更直观。

### ② 下行：控制指令

```
前端点"开泵" → POST /api/device/command
            → device_service 发 MQTT plant/edge01/cmd
            → ESP32 收到，用本地安全规则判断能不能执行
            → 回报 plant/edge01/cmd_ack
            → 后端更新 ControlLog
```

### ③ 实时视觉与每分钟帧元数据（✅ 不保存图片）

```
ESP32-CAM cam01 → MQTT status（stream_url / snapshot_url）
              → 后端发现动态地址 → /api/vision/live 代理 MJPEG → 前端实时窗口
              → 每 60 秒 GET /capture → CameraFrame 仅记时间、类型、字节数、结果
              → JPEG 立即丢弃，当前不调用 AI
```

### ④ AI 诊断闭环（后续阶段）

```
定时任务 / 用户点击 → 摄像头抓图 → 调 DeepSeek 分析
                  → 结果存 VisionRecord
                  → need_spray 为真 → control_service 下发喷雾意图
                  → ESP32 按"每日次数上限"决定是否执行
```

## 3. 职责划分（改代码前先想清楚该放哪层）

| 目录 | 只做这些事 | 不要做这些事 |
|---|---|---|
| `backend/app/api/` | 解析请求、调 service、返回结果 | 写业务逻辑 |
| `backend/app/services/` | 真正的逻辑：入库、阈值判断、闭环决策、调 AI | 直接碰 MQTT 报文细节 |
| `backend/app/db/` | ORM 模型与 Session | 写业务规则 |
| `backend/app/mqtt/` | 收发报文、断线重连 | 写业务规则 |
| `edge/main/` | 采集、控制、上报、本地安全 | 依赖网络可用性 |
| `frontend/src/api/` | 调接口、统一错误处理 | 写业务判断 |
| `frontend/src/views/` | 展示与交互 | 直接调 axios（必须走 `api/`） |

## 4. ★ 安全设计的核心原则

**执行器的安全策略必须实现在边缘端本地，不能依赖后端。**

后端下发的 `cmd` 只是**意图**，例如"开泵 3 秒"。板子收到后要自己判断：

| 本地保护 | 作用 |
|---|---|
| 水泵单次最长运行时间 | 防止抽水过头淹根、烧泵 |
| 两次运行的冷却间隔 | 防止频繁启停损坏继电器 |
| 喷雾每日次数上限 | 防止农药残留超标 |
| 补水与施肥互锁 | 防止同时动作导致浓度失控 |
| 看门狗 | 程序卡死时自动关闭所有执行器 |

**为什么？** 网线一拔、WiFi 一断，后端就管不到设备了。如果"水泵最多抽 10 秒"
这条规则写在后端，断网时水泵可能一直抽下去 —— 把植物淹死，甚至烧坏水泵。

后端这边只做**决策与记录**：
- 判断"该不该浇水"（基于传感器趋势）
- 记录每一次动作与结果（`ControlLog`，用于安全追溯）
- 在页面上明确标注"已下发" ≠ "已执行"

## 5. 技术选型与理由

| 部分 | 选择 | 为什么 |
|---|---|---|
| 边缘端 | ESP32-S3 + ESP32-CAM，均用 ESP-IDF | `edge01` 负责感知/执行；`cam01` 是独立视觉节点，避免不同芯片 target 混编 |
| MQTT | Mosquitto | 轻量、标准、Windows 上可直接跑 |
| 后端 | FastAPI + SQLAlchemy 2.0 | 自动生成接口文档，Pydantic 做数据校验能在启动时就发现字段写错 |
| 数据库 | SQLite | 课程设计单机够用，将来换 MySQL 只改 `.env` 一行 |
| 定时任务 | APScheduler | 纯 Python，`BackgroundScheduler` 跑在独立线程，不阻塞 Web |
| 前端 | Vue 3 + Vite | 组合式 API 写起来直观；Vite 开发时热更新极快 |
| 状态 | Pinia | Vue 3 官方推荐，比手写全局变量清楚 |
| 图像 AI | DeepSeek 视觉模型 | **只有 `deepseek-flash` 支持图像输入**，`deepseek-v4-pro` 是纯文本模型 |

**刻意没有引入的东西**：UI 框架（Element Plus 等）、图表库、ORM 迁移工具。
理由是保持轻量，需要时再加 —— 比如 ECharts 留到阶段 3 画曲线时再装。
